## 符号执行给你什么

符号执行器（KLEE）**符号化地**探索程序路径：不喂给它一个具体输入，而是把
输入当作变量，推理这些变量的所有取值组合能走到的所有路径。当它发现某条路
径违反性质——断言失败、内存错误——它就产出一个**测试用例**：必然能到达该
失败点的具体输入字节。在 KLEE 里，这些结果以 `.ktest` 文件的形式落盘，每
条违反路径一个文件。

所以一轮 KLEE 跑完，你手里可能有 200 个 `.ktest` 文件。每一个都是"哪个输
入能弄坏它"的答案——同时也是某个更难的问题的开头。

## 反例之后的空白地带

"哪个输入违反性质"并不是工程师接下来需要的东西。他们需要：

- **分诊**——200 个反例里，哪些是真 bug，哪些是测试皮建模错误，哪些是同
  一根因的重复？
- **理解**——对真的那个：执行为什么走了这条路径？每个分支点上变量的值是
  什么？不变量到底在哪一步被破坏？

今天的做法全靠手工：打开 GDB，自己解析二进制 `.ktest` 格式，自己重建
harness 期待的输入文件，把分支条件逐个手敲成断点。每个反例都从零来一遍。
慢、易错，而且面对成百上千的发现量完全不可扩展。

## symrepl 做什么

一条命令：

```
symrepl test000042.ktest --target ./parser
```

- 解析 `.ktest`，按 harness 契约（argv / stdin / 文件）注入记录的输入；
- 在目标上打开 LLDB 会话；
- 沿约束该路径的分支设好断点；
- 在每个决策点导出程序状态，让路径条件与调试器看到的机器状态始终对齐。

你仍然在一个正常的调试器会话里工作——symrepl 只是让反例变得**可导航**。

## 这是谁的工具

- **安全工程师**：分诊符号执行与模糊测试管线的产出（"发现"与"确认"之间
  的空隙是漏洞分析里最贵的部分）。
- **开发者**：CI 里跑着 KLEE，本地需要复现 `.ktest` 失败的人。
- **教师与研究者**：演示路径条件如何逐分支"驾驶"执行。

## 术语表

| 术语 | 含义 |
|---|---|
| 反例（counterexample） | 符号执行器找到的、违反被检查性质的具体输入 |
| 路径条件（path condition） | 约束一条具体路径的所有分支决策的合取 |
| `.ktest` | KLEE 的二进制测试用例格式：每个反例一个文件，每个符号变量一个具体值 |
| 分诊（triage） | 判断某个报告的失败是否真实可达的 bug——以及哪些共享同一根因 |
| 测试皮（harness） | 让 KLEE 等工具能驱动目标的小适配层：把输入从文件/stdin 喂给目标 |
